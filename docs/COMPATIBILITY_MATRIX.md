## Compatibility Rules

- Tooling selects the upstream Framework via `${fastddd-framework.version}`; it must not reuse its own `${revision}`;
- Tooling's internal modules uniformly use this repository's `${revision}`;
- Stable Tooling releases depend only on published Framework GA/RC artifacts — never on sibling source directories or locally-overridden SNAPSHOTs;
- Templates and generated results must record the target Framework version; the Tooling version must never be written as the Framework version;
- Database-shaped generated projects must carry an explicit connection-pool dependency in the pom: the default HIKARI renders `spring-boot-starter-jdbc` (version managed via the Boot parent), explicit Druid renders `druid-spring-boot-3-starter` with a pinned `<druid.version>` (aligned with the fastddd-bom managed value) — they must not rely on incidental transitivity from framework modules such as fast-ddd-crud/event (after the C4 dependency-boundary remediation, crud no longer transits any pool implementation; ECO-007A);
- Database-less shapes (`databaseType=NONE`) must not be added to the database runtime stack (pool dependencies are guarded by databaseType);
- The generated configuration's `fastddd.monitor.sql.slow-query-threshold` must be a plain numeric milliseconds literal (the framework's `SqlMonitoringProperties.slowQueryThreshold` is a `long` and does not accept Spring Duration unit suffixes; `1000ms` throws NumberFormatException at binding time; ECO-007A);
- New certified combinations must update the YAML, the contract tests, and the release notes together.
